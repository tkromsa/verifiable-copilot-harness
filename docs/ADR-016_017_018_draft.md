## ADR-016 — Renumber the release line from 6.x to 0.7.0

- Date: 2026-07-25
- Status: Proposed
- Decision: The next release is v0.7.0, not v6.16.0 or v7.0.0. The 6.x line ends at
  v6.15.1.
- Context: The 6.x numbering implies a maturity the harness does not claim; the owner
  assesses the product as pre-1.0. ADR-017 introduces a breaking architecture change
  (template removal, mode collapse), which is the natural moment to renumber. ADR-010
  keeps filenames version-independent, so a version change touches only artifact-internal
  cells and documents, never filenames.
- Options: (a) continue as v6.16.0; (b) jump to v7.0.0; (c) renumber to v0.7.0.
- Rationale: A single documented renumbering at a breaking boundary is cheaper than
  carrying a misleading maturity signal. 0.x honestly communicates pre-1.0 status to new
  users and to the target audience (non-expert departments).
- Consequences: Version strings updated in cells (00_Skills title A1, 00_Landing title
  and Harness Version row, __STATE B18 and B40, __TEST_ORACLE version cells,
  __ROUTING_ORACLE title), copilotstart.txt header, custom instructions header, README,
  cheatsheet, manifest, wiki Home badge. Git tag v0.7.0 with release notes explaining
  the renumbering. Old v6.x tags and releases are kept with a deprecation note.
  Historical ADRs keep their original v6.x release identity (ADR-015 restored that
  identity; this ADR does not rewrite history).
- Rollback: Re-tag; v6.15.1 remains the final 6.x release in git history.
- Evidence: Owner decision 2026-07-25; PLAN_v0.7.0.md Phase 0.

## ADR-017 — Single-kernel architecture: remove VCH_ProjectTemplate.xlsx, generate delivery sheets at fork, collapse modes 5 -> 3

- Date: 2026-07-25
- Status: Proposed
- Decision: Ship one workbook, VCH_HarnessCore.xlsx. Embed a new __DELIVERY_SCHEMA sheet
  holding the canonical definitions of the 9 delivery sheets (01_Plan .. 09_Worklog).
  PROJECT-FORK generates the delivery sheets from __DELIVERY_SCHEMA instead of copying a
  physical template. Workbook modes collapse to HARNESS, PROJECT, MIGRATION.
  This supersedes the five-mode set of ADR-011; ADR-011 is kept as history.
- Context: A cell-level diff of v6.15.1 shows 00_Skills, Project.Rules, Lists, __ADR,
  __GLOSSARY and __ROUTING_ORACLE are byte-identical between the two workbooks;
  __TEST_ORACLE differs in 1 cell (filename), __STATE in 6 identity cells, 00_Landing in
  content. The template's exclusive content is 9 delivery sheets containing only a title
  and one header row each — zero data rows. The two-workbook model forces the
  PROJECT-CREATION mode, duplicate-catalog validation, "never concatenate" rules and
  lockstep maintenance of two identical catalogs, and is the reported onboarding blocker
  for non-expert users.
- Options: (a) keep both workbooks; (b) keep the template, drop HarnessCore; (c) single
  kernel with embedded __DELIVERY_SCHEMA and fork-time generation.
- Rationale: One source of truth removes the entire duplicate-authority problem class.
  The fork flow already ends with a reopen-and-verify gate, which covers generated
  structure; harness_lint gains a check validating a forked v001 against
  __DELIVERY_SCHEMA. Delivery headers are data, and data belongs in the catalog artifact,
  not in a second physical file.
- Consequences:
  - Canonical mode enum becomes {HARNESS, PROJECT, MIGRATION}; Allowed_Modes values are
    ALL or a comma-space subset of these.
  - PROJECT-FORK Allowed_Modes becomes "HARNESS, MIGRATION" (fork converts non-project
    work or migrates; a running project never re-forks).
  - PROJECT-GUIDE Allowed_Modes becomes "PROJECT, MIGRATION".
  - SOURCE SELECTION reduces to: attached current project workbook -> PROJECT, otherwise
    core -> HARNESS; MIGRATION only for old project plus current core.
    AMBIGUOUS_LINEAGE survives only for multiple candidate project revisions.
  - The template 00_Landing QUICK START merges into the core 00_Landing.
  - __GLOSSARY, Lists, __TEST_ORACLE drop TEMPLATE and PROJECT-CREATION entries.
  - __ROUTING_ORACLE keeps 55 fixtures; exactly 3 are rewritten (RT-031, AV-002, AV-009
    — the only fixtures referencing the removed modes or the template by name, per scan
    of v6.15.1). Keeping the count avoids changing the lint constant and every "55"
    reference across README, starter, instructions and wiki.
  - harness_lint validates one workbook plus the new v001-vs-__DELIVERY_SCHEMA check;
    manifest loses the template entry.
  - "Start a project directly" quick start becomes: attach core, `load vch`,
    `new project`.
- Rollback: Restore v6.15.1 artifacts from git (template file and five-mode texts);
  the v6.15.1 tag remains intact.
- Evidence: Cell-level workbook diff (2026-07-25); routing fixture scan 3/55
  mode-dependent (2026-07-25); PLAN_v0.7.0.md.

## ADR-018 — Universal NEXT footer and extended Status Card Next line

- Date: 2026-07-25
- Status: Proposed
- Decision: Every reply ends with a next-step recommendation. Lifecycle replies keep the
  Status Card with an extended Next line; all other replies end with a one-line NEXT
  footer. Recommendations are drawn deterministically from May_Chain_To, filtered by
  Allowed_Modes for the current mode.
- Context: The Status Card Next line exists only after lifecycle events (load, guide,
  gate, commit, status request, Resume_From change). FOCUS MODE ends replies with a next
  step. Ordinary question-answer replies give no guidance, which is the reported failure
  mode: a non-expert user does not know what to do next or which skill applies. The
  00_Skills.May_Chain_To column already encodes the intended continuations (e.g.
  SHAPING -> WRITING-PLANS -> PLAN-DEEPENING -> VERIFICATION-CHECKLIST -> COMPOUND ->
  UPDATE-CONTEXT), so the recommendation needs no inference.
- Options: (a) extend the full Status Card to every reply (rejected: too heavy);
  (b) rely on PROJECT-GUIDE on demand only (rejected: requires the user to already know
  to ask); (c) lightweight universal footer plus extended Status Card Next line.
- Rationale: A deterministic, lint-verifiable recommendation source preserves the "no
  inferred state" philosophy. The footer is a proposal only; the existing rule against
  automatic chaining is unchanged — the user always invokes the next skill explicitly.
- Consequences:
  - Status Card Next line format becomes:
    `Next: <one concrete action> | Skill: [skill: SKILL-ID] or none | Why: <short clause>`.
    The Status Card remains the final block; the footer never competes with it because
    for lifecycle replies the footer IS the Status Card Next line.
  - Non-lifecycle replies end with: `NEXT: <action> ([skill: SKILL-ID])` or `NEXT: none`.
  - Exceptions mirror the Status Card exceptions: purely informational answers, SCRUB
    output, focus mode toggling and routing oracle runs carry no footer.
  - Recommendation rules: only May_Chain_To targets of the skill just used; drop targets
    whose Allowed_Modes exclude the current mode; if May_Chain_To is NONE, propose
    `update context` in PROJECT mode, otherwise `none`; never chain automatically.
  - copilotstart.txt and copilot_custom_instructions.txt gain a NEXT FOOTER section;
    cheatsheet and wiki Usage Guide document it.
- Rollback: Remove the NEXT FOOTER sections; the Status Card reverts to the v6.15.1
  format.
- Evidence: Catalog chain analysis of 00_Skills.May_Chain_To (2026-07-25); reported
  onboarding failure mode; PLAN_v0.7.0.md.
